# Patient runtime v1

Use `from patient_intake import PatientIntakeService, POLICY_VERSION` from a server with the deployed app/ on its import path. The policy edition is `patient-runtime.v1`. Each patient opens an O-owned encounter after local storage consent. Construct the service with a server-owned interview reducer, optional provider adapter, optional approved `provider_identity=(provider_id, provider_version)`, optional handoff callable, an optional encounter-owned provider factory (`provider_bindings`), and an encounter turn limit (default 8, maximum 32). Keep any stateful provider adapter local to its encounter. The default configuration makes zero provider calls. An identity identifies a particular approved adapter and edition; operator review of intended use, terms and configuration precedes injecting it. If the clinical content edition is unknown, record that limitation with the release.

| Service operation | Effect |
| --- | --- |
| `view(handle)` | Return the current display record. O enforces ownership and expiry. |
| `edit(handle, expected_revision, *, description, context)` | Start a new interview from the current patient statement and context. Clear transmission consent, prior continuation, derived results and confirmation. Preserve used turns. |
| `consent(handle, expected_revision, *, granted)` | Record explicit transmission consent against the server's policy and provider identity. Renewing current owned-provider consent preserves the question and revision. A withdrawal clears the current result and continuation and retires the owned binding. Reset/delete the encounter via O to erase local storage. |
| `assess(handle, expected_revision)` | Explicitly submit the current interview. Reserve an in-progress revision and charge a turn before adapter invocation. On reply, commit only against that same revision. |
| `answer(handle, expected_revision, *, question_id, answers)` | Consume the current question's opaque `issuance_id` as question_id. Q validates choices, evidence review or text against the stored question. The next provider turn requires an explicit assess action. |
| `confirm(handle, expected_revision)` | Return an opaque in-process receipt for this completed result. The revision stays current. |
| `navigate(handle, expected_revision, *, confirmation)` | Verify current consent, completed state and receipt, call P with the server-owned handle, revision and assessment, then recheck revision. Absence of a destination integration yields `{"state":"no_reviewed_destination"}`. |

The view keys are `revision, policy_version, state, provider_id, provider_version, consent, description_status, reason, question, guidance, urgency, uncertainty, possible_causes, next_step`. States are draft, assessment_in_progress, awaiting_clarification, urgent, provider_stop, completed, unsupported and provider_unavailable. An unsupported age or language retains the unsupported_context reason across consent and assessment attempts. Only a valid interview edit restores eligibility, with fresh consent required. Urgent guidance is displayed immediately. Render plain text. Discard all previous display, confirmation and destination results on a stale/expired handle, an edit or a failed action. Only display the latest server revision. Never expose the full encounter snapshot, continuation, result secret or receipt to the browser. A provider suggestion and a navigation confirmation have separate provenance from a clinician order. Provider disclosure and vendor-side deletion require separate operational controls.

## Module interfaces

- O's opaque handle implements detached `read() -> (revision, dict)` and atomic `replace(expected_revision, dict) -> revision`. An empty dict means a new encounter. Server state holds `state`, `assessment` (current public view), `interview`, `calls_used`, `continuation`, `consent_identity`, `consent_policy` and `result_secret`. O enforces a hard session TTL. Discard a failed or superseded provider completion.
- Q implements `start(description, context)`, `prepare_question(provider_question, interview_data)`, `answer(interview_data, server_question, question_id, answers)` and `has_unresolved_evidence(interview_data) -> bool`. Data is JSON-safe and held server-side. Questions carry id, kind, prompt and options. Each option has id and label. The v1 kinds are single, multiple, text and evidence_review. Evidence review includes the proposed concept_id, label, presence, temporality and source_ref. The patient's confirmation, uncertainty or disagreement remains distinct from what the provider extracted. M assigns a new issuance ID on every presentation, stores the prepared question privately and displays only Q's `question_view(server_question)` projection. Ordinary completion requires Q's explicit finding that evidence is resolved.
- N implements `assess(interview_data, *, continuation=None)`. Each reply has exact state, provider_id and provider_version. Awaiting clarification adds question and an optional bounded server-only continuation. Completed and urgent replies include plain-text guidance and uncertainty, possible_causes (a list of labels), a normalized urgency code and next_step. The disposition table below defines all accepted combinations. Unavailable or unsupported adds an optional bounded reason code. Adapter errors and uninterpretable payloads withhold prior output. N owns physical HTTP-call budgets, timeouts and concurrency. M owns the lifetime turn budget and performs no automatic retry. Consent revocation and edits invalidate outstanding replies via revision checks. Already dispatched work cannot be recalled.
- P receives `handoff(handle, expected_revision, assessment)`. It verifies current state and independent authority/destination evidence. No submitted patient checkbox, ready flag, origin, order or provider-proposed procedure enters this interface. A route or provider lookup can require separate consent, destination evidence and budget. Failure to find an eligible destination leaves the completed assessment available.

MGP's optional disabled adapter supports only its documented mappings. Free-text survey startup, correcting extracted evidence, approved patient populations and independently verified orders require their own integrations and reviews. When a requested function cannot be represented, return unsupported or provider_unavailable. Engineering tests use invented provider exchanges. A public deployment requires approved hosting, transport security, session isolation, secrets, vendor agreements, privacy controls and clinical review.


## Normalized provider dispositions

| Provider urgency | Required state | Required next_step |
| --- | --- | --- |
| `self_care` | completed | null |
| `consultation` | completed | `{"kind":"consultation","specialty_code":null}` or the same shape with a specialty code |
| `consultation_24` | urgent | null |
| `emergency` | urgent | null |
| `emergency_ambulance` | urgent | null |

The adapter maps its own structured disposition to these codes. The runtime checks the exact combination before persisting the assessment. An unknown code, a contradictory state or next step, or an extra clinical-stop field invalidates the reply and clears previous guidance and confirmation. Only completed dispositions can enter the separately authorized handoff.


## Additive question contract

The runtime policy remains `patient-runtime.v1`. Extended questions carry `schema="patient-question.v2"`. Existing v1 requests, reducer calls and answer forms remain supported. Every extended question has the base fields `id`, `kind`, `prompt` and `options`. The optional `optional` field is an exact boolean and defaults to false. Q binds one question to the private interview and M adds an opaque `issuance_id`. Andrew submits the displayed issuance and current revision to `answer`. Revision and issuance checks precede processing any answer, including skip.

| Issued form | Patient action and private result |
| --- | --- |
| Optional single, multiple, text or catalog selection | Only the exact object `{"skip":true}` requests skip. Q records `skipped:true` and `answer:null`. Missing input, null, empty text and an empty selection cannot request skip. N sends a wire null only for a form with that documented serialization. |
| Documented group-wide unknown | A separately offered, explicit group skip carries the issued skip marker. N binds that action to the private provider question and sends every issued item as unknown. Ordinary item omissions never trigger this action. N withholds the action unless the provider documents it. |
| `item_presence` | Empty `options` and one to 16 issued `items`, each with `id,label,required,choices`. Each choice carries the offered `id,label`, with IDs drawn from present, absent and unknown. Submit `{"items":[{"id":item_handle,"presence":choice_id}]}`. Q accepts each issued item at most once, checks its own allowed choices, requires every required item, and stores explicit answers in issuance order. Omitted optional items stay omitted. N's group_multiple requires every item and disallows whole-question skip. |
| `quantity` | Empty `options` and issued `units` with `id,label,min,max,integer_only`. Submit `{"value":number,"unit_id":unit_handle}`. Bounds are finite, inclusive and specific to that unit. Integer units accept JSON integers only. The precision flag defaults to false only for documented continuous inputs. Reject ambiguous bounds, unsupported precision, non-finite values, booleans or invented units. Apply no rounding, conversions or preselected units. N binds a duration's evidence ID privately. |
| `catalog_selection` | `selection` is single or multiple. Options contain locally issued handles and labels. The private `catalog:{id,edition}` binds the approved catalog and context to the current survey, revision and issuance. Submit one offered handle for single, or a nonempty list of distinct offered handles for multiple. Q stores the ordered selection and its catalog provenance. N resolves handles against the same catalog, survey and demographic/language filters before serialization. |

Q exposes the schema, optionality, exact labels and form fields needed to render the question. The provider question ID, vendor resource IDs, catalog binding, evidence IDs, source references and continuation stay server-side. Withhold an unrepresentable form as a whole. A 16-option window cannot stand in for an entire catalog. A complete small list can be issued directly. Larger lists require a separate server-bound picker with current edition, filter, pagination and accumulated-selection checks. Page and search actions submit no clinical answer and consume no provider assessment turn. Until that picker and an approved complete catalog are available, withhold those lists.

The public assessment includes `description_status="uninterpreted"` when an interview holds the patient's verbatim description. For v1 stored assessments lacking this field, treat prose as uninterpreted. Display “Your description has not been interpreted.” An explicit catalog selection or reviewed extraction can establish evidence for those specific items only. It cannot certify interpretation of the whole description.

## Terminal provider stop

A recognized non-emergency stop with approved plain-text guidance uses exactly `state="provider_stop"`, `provider_id`, `provider_version` and `guidance` (1–2048 characters, with non-whitespace content). N checks recognized emergency reasons first and returns the existing urgent disposition. Unknown or malformed alerts withhold progression. M clears the previous result secret, question and continuation. The stop has no final urgency, causes, next step, receipt or destination. The UI displays guidance immediately and can start a new interview. Revoking and granting consent cannot resume the stopped interview.

## Encounter-owned survey binding

Pass a trusted zero-argument `provider_bindings` factory and an approved `provider_identity` to the service. The direct v1 `provider` and this factory are mutually exclusive. Use the owned path for integrations that create remote resources.

1. After current consent and the in-progress revision reservation, M calls `handle.bind_provider(reserved_revision, factory)`. O reuses the encounter's current binding or atomically installs a new one. The local factory reserves cleanup capacity and returns an adapter with `assess(interview_data, *, continuation=None)` and an O-issued `cleanup_reservation`. Binding, factory invocation and retirement perform local operations only. M invokes the adapter outside the session lock. No binding or vendor reference enters the display or the serializable encounter record.
2. O's process-owned, per-configuration `CleanupMailbox.reserve()` reserves the obligation before any remote create. A saturated mailbox blocks creation. For each role in users, patients, surveys order, N obtains a single attempt via `reservation.admit_create(role)`. After releasing locks, N performs the I/O and calls `settle_create(attempt, outcome=..., resource_id=...)`. The exact outcomes are created (verified vendor UUID), not_created and unknown. A retired reservation rejects new creates and retains late settlement for an already admitted attempt. A retired binding cannot publish a continuation.
3. An edit or withdrawal uses `handle.replace(current_revision, data, retire_provider=True)` to atomically detach the binding and retire its reservation. O also retires on reset, delete and expiry. Retirement closes admission locally and cannot wait on a vendor transport lock or remote deletion. A stale edit cannot retire another revision's binding. Repeated current owned-provider consent preserves the active binding. A change of provider identity or mode requires fresh consent.
4. A separately budgeted cleanup worker calls `mailbox.claim()`, disposes verified survey, patient and user resources in reverse creation order, then calls `finish(claim, disposed=(...roles...), retryable=True)` for that claim. Only a verified successful deletion or a documented already-absent response can settle a known resource. Partial disposal retains remaining IDs. Unknown delivery remains unresolved even if known IDs are gone. Store only bounded operational status, attempt/reservation identity, configuration reference and verified resource IDs. Keep transcripts, patient identifiers, tokens, sessions and callbacks out of cleanup records.

This engineering contract uses process-local ownership. Process loss and a deployment's durable vendor-disposal strategy require a separate operational decision. Clinical acceptance, live patient traffic and production activation require their own reviews.
