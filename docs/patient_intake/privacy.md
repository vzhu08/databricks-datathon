# Patient encounter storage and deployment boundary

The patient encounter store holds one current encounter in the server process for one Streamlit WebSocket session. It has no database, cross-session lookup, or restart recovery. The active lifetime starts at affirmative consent to the configured local-memory notice. The maximum is 15 minutes, with a shorter server-configured lifetime allowed. Edits, reads, and provider activity do not extend it.

## Server integration

Create one `patient_intake.session.PatientSession(notice_version=...)` inside the server-owned Streamlit session. Keep the instance and its current handle in that session alone. The notice version is a deployed constant. After explicit opt-in, `open(consent=True, notice_version=...)` creates an empty encounter at revision zero. Use the handle issued by that instance. Never create, resolve, or select handles from a form value, URL, cookie, or client-provided encounter ID. A copied identifier conveys no access. The Python handle is an internal server capability and shares the trust boundary of the UI and orchestration code.

`handle.read()` returns a detached `(revision, data)` snapshot. `handle.replace(expected_revision, data)` atomically replaces the snapshot only at the current revision. Accept patient input and provider results through the product's schema first. The store bounds an already validated JSON object; it does not classify which clinical fields are needed. For provider work, commit the in-progress state by compare-and-swap before dispatch and finish against that exact revision. An edit or newer transition makes the first completion stale. Treat a stale or unavailable completion as discarded and render the latest server state. Provider transmission requires its own explicit disclosure and authorization decision. Local-memory consent authorizes this store only.

`reset(handle)` and `delete(handle)` immediately drop the current snapshot. They invalidate that handle even if a new encounter returns to revision zero. A new encounter requires fresh affirmative consent. The server retains only a coarse lifecycle label after reset, deletion, or expiry. Access checks the monotonic deadline and an idle expiry timer also clears the retained snapshot. A server restart starts with an empty store. The expiry mechanism does not persist any identifiers or data.

## What the UI and orchestration must clear

- Request symptoms and context only for stated purposes. Avoid names, contact details, account identifiers, and unrelated history. Keep widget keys fixed and free of patient values. Limit the collection and the approved provider request to fields the flow actually needs.
- Keep raw descriptions, answers, evidence, provider bodies, and encounter tokens out of URLs, browser storage, application caches, analytics, transcripts, downloaded files, and logs. Live form and result values are necessarily present in the current tab's memory. Verify that widget keys/state, render history where controlled, and any local display copies are cleared on reset, deletion, expiry, and new encounter. Recheck the active handle/revision before rendering a result or using it downstream.
- If the host retains a disconnected session, treat reconnect as the same session only when the framework confirms ownership and the encounter is still current. Clear on any known account/session boundary change and reject stale callbacks. Never restore an encounter from URL state or a browser-provided snapshot.
- Display controlled error codes or fixed copy. Do not interpolate exception messages or patient values into errors or record traceback locals. Disable request/response body, WebSocket payload and form capture, session replay, debug reports with locals, and health-data collection by telemetry or proxy middleware. The module itself emits no logs.
- Treat snapshots passed to UI/orchestrator workers as short-lived. Deleting an encounter cannot recall a detached copy, unsend a provider request, remove text already viewed or manually saved, or guarantee overwrite of Python memory. Revoke unpublished results and discard worker copies. Evaluate provider-side processing, retention, deletion, and access independently before any real transmission.

## Hosting and release

Databricks Apps requires an authenticated Databricks account user with app permission. Its application service principal grants the application access to configured resources and does not identify patients. The existing Databricks source layout can verify the packaged flow with synthetic inputs. Databricks Apps does not support anonymous public access. [Databricks Apps permissions](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/permissions#organization-permissions) · [App authorization](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/auth)

Streamlit Session State is scoped to the WebSocket and can survive a brief disconnect. The store and its lock are deliberately process-local. They do not offer shared sessions, failover, or durable records. In a supported multi-instance deployment, keep HTTP and WebSocket traffic for the active session on its owning instance, or require a fresh session after the connection moves. A single timer is allocated for each active encounter, so bound concurrent sessions at the host and exercise capacity and idle cleanup under load before deployment. [Streamlit Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state) · [Streamlit client/server architecture](https://docs.streamlit.io/develop/concepts/architecture/architecture)

For external access, the deployment owner needs an approved host and region, an HTTPS/WSS ingress with server-owned session identity and bounded session admission, and end-to-end verification of body/log redaction and browser clearing. The provider, its data handling, the consent notice and deletion promises, and the intended clinical use still require the project release decisions. This module supplies an ephemeral storage boundary for integration.

## Provider cleanup and encounter binding

The cleanup mailbox is process-local and makes no requests. Configure one `CleanupMailbox` per trusted provider configuration, outside the browser session. An idle or disconnected session must not own the only copy of the cleanup metadata.

After consent and the in-progress revision reservation, use `handle.bind_provider(revision, factory)`. The trusted factory is local only. It reserves mailbox capacity before any vendor create, and its adapter exposes that `cleanup_reservation` and its `assess` method. It must release any unused reservation if construction fails. The session rechecks the revision before attachment and retires any discarded candidate. No transport runs during binding or retirement. Use `handle.replace(revision, state, retire_provider=True)` for provider withdrawal or interview restart. Reset, deletion and expiry also retire the reservation without waiting for a vendor response. If the process drops a disconnected session before its timer runs, the timer can still retire the mailbox receipt when the deadline arrives. It retains no adapter or patient snapshot.

Before each create, `admit_create(role)` issues a single-use attempt for the next role in order: users, patients, surveys. The adapter runs transport outside the locks and settles the attempt with a verified UUID, definite noncreation, or unknown delivery. A retired reservation rejects new creates. An already admitted create can settle after local erasure, and its verified references remain eligible for disposal.

A server-owned disposal worker claims pending references and reports confirmed deletions in reverse order. Partial deletion preserves outstanding references for bounded retries. Terminal failures and exhausted attempts retain their references for authorized review. Removing all known resources cannot resolve an ambiguous create. A full mailbox refuses new reservations. The mailbox holds only a small set of opaque vendor UUIDs and bounded operation state and exposes only counts for operational status. The adapter verifies ownership and must provision disposal attempts independently of the interview budget. The process composition and provider adapter still need to wire dispatch. Process loss, ambiguous creates, and exhaustion require a separately approved reconciliation or durable disposition strategy before live use.
