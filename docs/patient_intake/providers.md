Ask Infermedica to demonstrate patient correction of extracted facts and provide written India deployment terms before selecting it for patient use. ## Requesting an evaluation

1. An authorized organization representative uses the **Get in touch** link on the [developer portal](https://developer.infermedica.com/documentation/conversational-triage-api/). Supply organization, real contact and business email, role, and the intended English-language Indian patient interview. Specify **Conversational Triage v2**, not just an Engine developer trial.
2. Request a CT-provisioned sandbox instance ID, OAuth client credentials scoped to `ct:conversations`, applicable instructions for use and product version, and the written commercial/privacy answers above. Verify how to correct or retract evidence, flag unmatched findings, and delete a conversation. Keep client secrets and short-lived tokens in the server secret store. [Authentication](https://developer.infermedica.com/documentation/conversational-triage-api/basics/authentication/)
3. Proposed smoke budget for separate approval: **five total HTTP attempts**, one at a time, one invented interview, zero retries. Allow one token request, one instance-info read, one conversation create, one text turn and one assessment read. Stop at the first failure or budget exhaustion. This tests connectivity and one turn only. Require a vendor-agreed disposal procedure before the smoke. Record status, counts and version metadata without recording bodies or credentials.
4. For production, obtain intended-use, local clinical review, consent, hosting/processing agreement, price and activation approval. A sandbox token alone proves none of these. If CT access or evidence correction is unavailable, return to the decision owner with the actual blocker.

## Engineering handoff

`providers.transport.Transport` performs one TLS JSON exchange against a server-supplied host, operation and headers. A process shares one transport and its non-renewing attempt quota. Each encounter supplies a shared physical-attempt budget across turns. Configuration defaults to zero physical attempts. The service must separately reserve logical turns and coordinate deployment quotas across replicas/restarts. A deadline bounds the caller wait. A slow exchange retains a concurrency slot until it exits. No automatic retry occurs, including when the vendor may have accepted a timed-out request.

A successful `received` result contains an untrusted JSON object for the selected adapter to validate. Unmatched evidence, unknown answers, missing recommendations, unrepresentable questions and permanent termination need distinct handling at the adapter/runtime boundary. Only validated provider output may become clinical guidance. Tests inject invented replies into the exchange and never select a provider.
